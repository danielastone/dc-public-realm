# JS object renderer parity — branch contract

Branch: `js-object-renderer-parity`

This file exists to make the migration branch visible to pull-request CI before renderer code is added.

## Acceptance contract

1. Python production code, Python validators, deployment behavior, and the existing DOM contract remain unchanged.
2. JS renderer output is written only under `build/`; it is never written into `site/` on this branch.
3. Artigas is the first implementation target, but merge acceptance covers every published object enumerated by `publishedObjects()` / `pathFor()`.
4. Every JS object page must match the final Python object page under only the normalization rules already recorded in `docs/audits/html-parity-normalization.md`.
5. A mismatch is a renderer defect unless a new normalization is separately justified and recorded; comparison is not loosened merely to obtain parity.
6. Static completeness is durable: required page content — title, image, provenance fields, and navigation — must exist in prerendered HTML. Runtime JavaScript must not be required to populate it.
7. Current-state check: generated object pages contain no `<script>` elements. This is not a permanent ban on progressive enhancement.
8. Page content comes only from structured inputs declared in `lib/renderer-input-policy.mjs` and shared templates. The policy has two positive categories: materialized datasets, read from `build/data/`, and static configuration, read from `data/`. Logical names are stable contracts and paths identify the actual source layer. The declared materialized dataset is `object_overviews` → `build/data/object-overviews.json`; declared static configuration is `publication_dependency_rules` → `data/publication_dependency_rules.json` and `publication_status_rules` → `data/publication_status_rules.json`. Transaction and migration files remain upstream inputs to materialization and are not renderer inputs. `claim-modes.json` and `external-records.json` are not renderer inputs until a renderer unit actually consumes them. Changes to either input-policy category require review and a matching update to this contract. The JS driver reads each category from its declared layer directly; it does not reproduce Python publication's staging/copy-back mechanism. Renderer code must not copy or embed oracle/Python-rendered HTML or fragments from it, hard-code object-specific content that belongs in structured data, or branch on object identity to patch parity differences.
9. Before this PR leaves draft, scan renderer/template source for every published object's canonical name, slug, and entity ID. Any hit must be justified as non-content test/fixture data; production renderer/template hits fail the branch contract.
10. Rendered fragments are opaque after creation: they may be concatenated or interpolated into construction-time templates, but renderer code must not search, slice, regex-match, split, or rewrite rendered HTML. Transformations such as escaping are permitted only on data before it becomes rendered HTML. The mutation-pattern scan is a heuristic tripwire, not a proof; `escapeHtml()` is an explicit reviewed exception because it transforms input data rather than rendered output.
11. `epistemicsByAssertion` and `taskHtml` are retired. `renderObjectPage()` accepts structured epistemic context/dependency rules and structured research-task inputs; it renders both sections internally.
12. The branch is ready for review only after all published objects satisfy parity and static-completeness gates in CI and the object-specific-literal scan is clean.
13. Overview reconciliation preserves Python's failure semantics while adding JS type structure. Every semantic condition represented by the frozen mapping in `tests/overview-error-inventory.mjs` must abort rendering/building in JS as the corresponding Python condition does. `OVERVIEW_ERROR_CONDITIONS` is the single mapping authority for explicit Python raise site/condition → JS typed condition; this contract does not duplicate that condition list. Python also aborts implicitly on missing required mapping keys (`KeyError`) and invalid joined date values (`TypeError`); JS must preserve those aborts with `MissingRequiredFieldError` carrying `site: implicit:<field>`. These implicit sites are intentionally outside the explicit-raise inventory tripwire. Exact exception-message wording and Python's generic exception types are not parity requirements. A change in the frozen explicit Python raise-site set is a review event, not a reason to renumber site IDs until the inventory test passes.
14. Epistemic publication has three distinct layers and the renderer must not compensate for an invalid context. Whole-corpus context construction matches Python's eager order exactly: first require `assertion_id` on every evidence row; second run conflict validation (missing or duplicate `assertion_evidence_id`, and incomplete `CONTRADICTS` rows); third require `source_id` on every evidence row; fourth construct the lineage index; fifth construct `source_by_id` by requiring `source_id` on every `sources.json` record; sixth construct the conflict index. Only after those steps may publication-scoped rendering begin. Therefore a row missing both `assertion_id` and `assertion_evidence_id` aborts on missing `assertion_id`; an evidence row missing both `assertion_evidence_id` and `source_id` aborts in conflict validation; a bad source record is not reached if an earlier evidence failure aborts the build; and in the end-to-end build a `CONTRADICTS` row missing `assertion_id` aborts at the first whole-corpus check rather than as `INCOMPLETE_CONTRADICTS`. The eager evidence and source checks test key presence, matching Python subscripting, rather than truthiness. Direct validator/derivation tests may still exercise otherwise unreachable validator conditions. Duplicate source IDs follow Python dict-comprehension behavior: the last source record wins.
15. Once the context is valid, renderer-level epistemic failures are scoped only to assertions actually rendered for published objects. A derived dependency state with no entry in `publication_dependency_rules` aborts only when the published assertion has at least two evidence rows, matching Python's dependency block. A present `source_id` absent from `sources.json` aborts only when lineage is rendered for a published assertion. Equivalent defects confined to unpublished assertions do not cause renderer-level aborts. The JS epistemic renderer uses the already-proven derivation implementation; per-row lineage traversal is exported and invoked where Python invokes `trace_row()`, preserving Python's structure and avoiding a second traversal implementation.
16. The research-missions unit owns the entire object-page `Research missions` section, including heading, `data-open-task-count`, singular/plural summary, explanatory copy, task blocks, and the zero-task state. Task-detail and collaborate pages remain Python-owned and out of this object-page migration. Task status computation reuses `lib/status.mjs`; task presentation ports Python's `pred()` and `public_status()` and does not consume `publication_status_rules.json`. The GitHub submission query uses a narrow Python-`quote_plus` equivalent: ASCII alphanumeric plus `_ . - ~` are literal, space becomes `+`, and other bytes are percent-encoded.
17. Research-task failure scope follows the executable caller path. During eager task indexing, only tasks whose `status` equals `OPEN` subscript `object_entity_id`; a missing key on an open task aborts before object rendering, while non-open tasks are not read by that pass. During object-page rendering, required task fields (`task_id`, `title`, `research_gap`, `high_value_result`, `repository`, `collection`, `critical_rule`, `status`) and each target's `desired_evidence` / `desired_effect` are subscript-equivalent key-presence requirements only for open tasks belonging to the rendered object. An unknown target `assertion_id` is deliberately not an error: its label falls back to the ID. Python's task-detail and collaborate pages impose additional all-task field requirements; those remain enforced by Python CI and are not duplicated in the JS object renderer until those pages migrate.
18. Base-page rendering consumes `publication_status_rules.json` for assertion labels and stable rule IDs and preserves Python's missing-rule abort at the assertion/related-assertion render site. Direct assertions and predecessor/lineage assertions share the same assertion body but preserve their distinct `data-assertion-id` / `data-related-assertion-id` attributes. Predecessor/lineage inclusion follows Python's predicate-derived subject set and assertion-file order. The JS shell emits the final post-navigation header directly: `site_state()` first inside `<header>`, then the publication kicker, then the fixed `primary_nav()` markup. The Python navigation rewrite is not reproduced as a mutation pass. Python's hard-coded `OBJECTS`/`SLUGS` enumeration is deliberately not ported; JS remains metadata-driven through `publishedObjects()` / `pathFor()`, with parity requiring the currently published IDs/routes to agree.

Golden-file freezing remains deferred until Python retirement.
